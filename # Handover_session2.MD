## Issues uncovered (pre-existing, surfaced by Test 5)

### Issue 1 — Stripe webhook URL still pointed at `raredex.co` ✓ FIXED

**Status:** RESOLVED in Stripe dashboard.

The webhook endpoint was configured at `https://raredex.co/webhook/stripe`
from before the GrailSweep rebrand. Cloudflare was 301-redirecting to
`grailsweep.com`, and Stripe doesn't follow redirects on webhooks. Result:
**every real-money webhook since the rebrand had silently failed**. The
May 17 admin test entries in `subscriptions.json` were synthetic
(`pi_test_*`, `sub_test_*`) and bypassed the real webhook flow, which is
why nothing flagged this earlier.

Fix applied: Stripe Dashboard → Webhooks → endpoint URL updated to
`https://grailsweep.com/webhook/stripe`. Signing secret unchanged.

### Issue 2 — Cold-start exceeds Stripe's 10s webhook timeout — OPEN

**Severity:** Blocks Play Store launch.

The Modal app serving the webhook is the same one that runs CLIP /
DINOv2 matching. Cold container takes ~16s to warm up (model loading,
embeddings cache). Stripe's webhook timeout is 10s. Result on every
cold-container webhook:

- Stripe times out at 10s → marks delivery failed
- Modal handler still finishes at ~16s → code generated, saved, emailed
- Stripe retries 1 hour later → hits warm container → generates a
  **duplicate code** for the same payment

Confirmed live during today's test: TOPUP-3F7X-ZYK4 generated by
manual webhook resend at 11:49, Stripe's automatic retry would have
created a duplicate code at ~12:49 if webhooks hadn't been disabled.

**Three fix options:**

| Option | Effort | Cost | Pros | Cons |
|---|---|---|---|---|
| Separate lightweight Modal app for webhooks (no GPU, no models) | Medium | Low | Cleanest architecture, instant warm | New deployment to maintain |
| Set `min_containers=1` on current Modal app | Trivial | Constant container cost | Zero code change | Pays for idle compute 24/7 |
| Async webhook handler — return 200 immediately, process in background | Small code change | Free | Eliminates timeout entirely | Slight code complexity |

Recommendation: option 3 (async handler) is the cleanest fix that
doesn't add infrastructure cost. Option 2 is the fastest interim
fix if shipping urgency wins.

### Issue 3 — Free-tier display ignores top-up credits — OPEN

**Severity:** Cosmetic only. Credits work correctly behind the scenes.

In `app.py:465-466`, the free-tier branch of `inject_scan_state()`
sets `topup_rem = None` when the user still has free scans
remaining (count < FREE_TIER_MONTHLY_LIMIT). Result: usage modal
displays "0 top-up scans" even when 75 are sitting in modal.Dict.

Confirmed: after using all 25 free scans, the modal correctly
shows the top-up balance and scanning proceeds normally consuming
from top-up credits.

**Recommended fix (from recon, app.py:465-470):**

```python
# Current (buggy):
if not allowed:
    topup = _db.read_topup_credits(server_fp, device_id)
    topup_rem = topup.get("credits", 0) if topup.get("ok") else 0
    allowed = topup_rem > 0
else:
    topup_rem = None

# Fix: always read topup balance, then use it for the gate
topup = _db.read_topup_credits(server_fp, device_id)
topup_rem = topup.get("credits", 0) if topup.get("ok") else 0
if not allowed:
    allowed = topup_rem > 0
```

One-line change in spirit — replaces the `if/else` with always-read.
Adds one modal.Dict round-trip per free-tier page load.
